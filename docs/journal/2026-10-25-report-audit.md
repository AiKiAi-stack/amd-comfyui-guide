## 为什么 Windows 某些记录慢很多

此前没有完整控制变量，表里的秒数不能用来评判操作系统优劣。新版逐例列出计时边界，并在每组提供权重、编码器、输入 SHA/顺序、提示词 SHA、输出尺寸、seed/采样/LoRA、编码设备、精度和分阶段方式的核对表。相同文件名不等于已核验跨平台完整 SHA。缓存冷热、存储、驱动/软件构建尚未统一。

| 例子 | Windows 原观测 | Linux 对应变体观测 | 已确认差异 / 限制 |
| --- | --- | --- | --- |
| Turbo UN 文生图 | 526.25 秒 | 96.665 秒 | Windows 明确使用 CPU 文本/视觉编码规避卸载崩溃；Linux 此次使用 GPU 编码，且分进程。不能算系统加速倍数。 |
| FLUX Klein GPU-text 文生图 | 210.85 秒 | 44.317 秒 | Windows 为原 safetensors 编码器，Linux 改现有 Q4 GGUF 文本编码器并分进程；不是同权重精度实验。 |
| Kroma 狐狸文生图 | 285.03 秒 | 58.376 秒 | 运行配置与分阶段方式不同，历史实际 dtype、冷热缓存未完整记录；无法据现有证据分摊各因素贡献。 |

抽查 Windows 原生 history：Turbo UN execution_start→success 为 524.850 秒，FLUX GPU-text 为 208.104 秒，与各自观测值接近。因此这些高耗时不能主要归因于排队误计，也不能据此证明 Linux 数学内核快几倍。另有部分历史结果只有整批耗时，新版单独标记，不能当单案例耗时。

Linux 的编码、采样阶段观测均包含相应阶段的模型加载/搬运及结果收集；“采样阶段”还包含 CPU 解码、保存，不是 GPU 内核纯采样。分阶段进程总计由各阶段 total_seconds 求和，另包含启动/准备/清理。原始 execution.json 不改写。

若要判断操作系统差异，需重新执行两平台一致的权重 SHA、输入/顺序、完整提示词、seed、尺寸、步数/CFG/调度器、设备分配、dtype、offload 与进程方式，分别记录冷启动和热运行，至少重复三次，分别统计编码、去噪、解码和总计。当前 Ubuntu 结果不能补造缺失的 Windows 受控试验。

## 为什么 Linux 原记录失败但 Windows 有图

“同功能有图”和“原配方原样通过”是两个问题。Linux 旧尝试保留 NaN、内存保护停止、过慢中止；后来 CPU 编码、分进程、分块解码或更换文本编码器成功时，另立案例并列出差异。新版不再用“Windows 配方未在 Linux 重跑”这种容易误读的全局标签；Linux 结果从独立记录读取。

当前已有的 40 组图片包括未达目标的真实图片，不能把有 PNG 等同功能通过。换脸身份、视角、水彩转换、蝴蝶结大小、背景额外文字及补图接缝仍各自保留部分达到/未达到结论。

## Linux 原因与方案

汇报每个功能下方的“Linux问题”关联具体失败/效果不足案例，逐项列出已确认、未确认、已做尝试、解决或规避、未完成工作。结构化数据见 [Linux问题清单](../../trials/2026-10-25-report-audit/linux-issues.json)。

- GPU 参考编码的正/负向条件全 NaN：位置已确认，底层算子还是 GGUF 部分加载/卸载根因未证实。BF16 单改仍失败；CPU/BF16 编码→新进程 GPU 采样已出图，是规避方案。
- 可用 RAM 低于 1536MiB：控制器保护中止，不能写为原生 OOM 或系统不支持。FLUX 改 GGUF 编码器、MOSS 改 CPU 编码、AIO 分开加载 checkpoint 组件已有实际输出；原单进程问题未结案。
- FLUX 1024 在 4/4 采样完成后 CPU 解码触发保护：改 tile256/overlap64 的分块解码已产生 1024 图片，最低观测可用 RAM 约4022MiB。额外背景文字仍未解决。
- 8B CPU 反推约312秒仅12 token，主动停止：4B GPU 视觉辅助→8B CPU 编码→Base GPU 采样已跑通，保留生成原文与 SHA；这不等于原8B反推性能修复。
- MOSS 水彩转换：只改 denoise 0.6→0.85 仍输出照片风格；未证实模型、LoRA或提示词各自责任。后续固定输入/seed进行 LoRA 与步数单变量对照，尚未完成。

本轮修正证据展示与范围，不以重复相同失败掩盖未完成工作。原始执行、失败结果和图像继续可追溯。
