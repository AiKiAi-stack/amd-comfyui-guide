## 实际执行与使用边界

新 Linux 输出多数使用两个独立进程（4B辅助反推案例另有独立的文字生成阶段）：阶段 1 保存精确 conditioning / reference latent，结束进程；阶段 2 校验归档 SHA256 后重新加载扩散模型采样和解码。每个阶段的 API、提交回执、history、输出和最低观测可用 RAM 分开保存，主结果绑定两个进程与原整图 SHA256。单张图片出图不证明普通整图、同进程重载、真实卸载或 OOM 恢复通过。

本机“模型功能库 / 模型 / 功能”中优先使用已出图案例的 `02-采样.json`，默认指向已校验的对应归档。更换提示词或输入时先运行 `01-编码.json`，记录文件和 SHA256，重启服务，再更新采样图的 LoadRepairConditioning。画布说明和汇报的复现步骤给出本例的实际启动参数；编码和采样配置不同时分别列出。整图只作配方展示的文件不默认安装。

完整包包含 UI、API、输入和编码归档，不包含模型。轻量包不含编码归档，换机器后必须先编码。前端导入/导出一致、执行出图、图像健康与功能达标各自记录，不互相代替。输入与遮罩预览不计生成结果；后续失败不会隐藏已有图片。

## Qwen 数值问题与规避

GPU 参考图编码出现非有限数：最小诊断定位到 `positive[0][0]` 或 `negative[0][0]` 的文本向量全部为 NaN；不是正常注意力遮罩中的负无穷。FP16 与单独改 BF16 均保留失败记录；同 BF16 配方有一次独立编码通过，说明不能把偶然成功当作问题已消失。

8B CPU自回归尝试约312秒时只在停止请求前生成12个token，因延迟主动中止；8B GPU/BF16+backing候选触发1536MiB保护。两者均无完整描述或图片。现有4B视觉语言模型单独验证约40秒生成完整准确句子，辅助三阶段流程另行记录，不升级原8B反推配方。

归档检查器只增加错误路径、形状、dtype 和 NaN/Inf 数量，不更改模型计算，也不清洗或保存无效张量。CPU/BF16 编码 → 独立 GPU 采样的对照得到有效归档和真实多图输出；CPU 与 GPU 两个阶段的启动命令分别记录。该方法记为规避，不称为 GPU 编码根因修复。原 GPU 失败、诊断通过和新 CPU 尝试均保留。

## 其他模型与质量结论

Kroma 采用分进程编码/采样；单独关闭 pinned/mmap 的有限观察不证明加载永久死锁或根因修复。无狐狸主体的参考裁图已得到猫头鹰，完整狐狸参考仍保留主体串入的失败。换头、混合背景等按实际输出保留部分达到。

FLUX.2 的 Linux GGUF 文本编码变体保留原扩散权重，但不同于 Windows 普通文本编码器。1024 普通解码保护停止保留，改为 CPU 分块解码后取得真实 PNG；HELLO 清楚，背景额外文字仍未消除。双壶嘴和小蝴蝶结等细节按各自图片判定，不因出图而升级。

MOSS 使用配套的 SFT INT8 扩散、9B 文本权重与 DMD LoRA；CPU 编码没有替换成其他模型。提高图生图 denoise 的独立对照仍未获得明确水彩风格，原0.6与0.85两次结果都保留。AIO 通过按阶段仅加载所需 checkpoint 组件降低内存，继续调用核心加载接口，不替换模型数学实现。

这些项目不虚构 Linux 图片。Windows 的身份、LoRA、CPU8B、视频和 native 卸载等旧待办不由本轮 Linux 图片结案。
